这篇文章是给谁看的？

  • 你让 AI 写过代码，但出来的东西"浑成一坨"，改一个功能炸三个地方
  • 你听说过"分层架构"、"MVVM"、"DDD"这些词，但不知道它们是什么意思
  • 你希望 AI 生成的代码结构清晰、容易修改，而不是一锅粥

引子：为什么需要架构？

先说一个真实场景。

你有天让 AI "帮我做个报销 App，能提交报销、审批、查看历史"。AI 很听话，刷刷刷写出来了。

看起来功能都有。但过了几天你想改一个东西——"报销上限从 10000 改成 5000"。

然后你发现：

改一个数字 → 炸了三个页面
提交页面的上限改了 → 审批页面的没改 → 历史页面的也没改
因为 AI 把"上限 10000"这个数字写在了 5 个不同的文件里

这就是没有架构的后果。

架构的作用，就是确保改一个东西，只改一个地方。

第一章：三问定需求——写代码前先问自己

很多小白犯的第一个错误：拿到需求直接让 AI 开写。

在写任何代码之前，先问自己三个问题。这比看懂代码更重要。

第一问：价值锚点——做这个东西到底是为了什么？

❌ 模糊说法："让用户更好地社交"
✅ 合格说法：针对新用户，解决不知如何开口的孤立感，
   在注册后3分钟内自动引导至兴趣匹配群聊

❌ 模糊说法："做个报销 App"
✅ 合格说法：让员工 30 秒内提交报销单，
   审批人手机上 10 秒完成审批

如果无法清晰定义核心价值，这个需求大概率是个"功能废墟"。

第二问：第一动作——用户进来第一件事做什么？

找到用户进入产品后最核心的唯一路径：

❌ 用户进来看到一堆东西：好友列表、群聊广场、个人设置、动态发现
✅ 用户进来只看到一条路：登录 → 找人 → 发消息

❌ 报销 App 用户进来：看到统计图表、待办列表、历史记录、个人信息
✅ 报销 App 用户进来：打开 → 拍照上传小票 → 填写金额 → 提交

用户如果停顿一秒想"我该点哪"，设计就是次品。

第三问：Not-To-Do——明确不做清单

这可能是三个问题里最重要的一个。

大多数项目死掉，不是因为做得太少，而是因为做得太多。

✅ 先列清楚哪些功能当前版本绝对不做
✅ 每个"顺便做一下"都会让代码复杂度翻倍
✅ AI 不会拒绝你——你让它加功能，它就加，哪怕代码已经快炸了

这三个问题的质量，决定了代码的寿命。

第二章：三层架构——所有架构的基础

厨房比喻

想象你开了一家餐厅：

不分层（Vibecoding 默认产物）：
  一个人干所有事：买菜→洗菜→切菜→炒菜→洗碗→收银→招呼客人
  要换菜单——得把这个人从头到脚换一遍

分层（专业做法）：
  🖼️ 前台（UI层）→ 只负责"画界面"
  👨‍🍳 后厨（业务层）→ 只负责"做菜"
  🧊 仓库（数据层）→ 只负责"管东西"

  换菜单只改前台，换供应商只改仓库

三层架构在 Flutter 中的映射

你用 Flutter 开发 App，代码分三个文件夹：

lib/
├── data/              ← 🟢 数据层：只管增删改查
│   ├── models/        ←   数据长什么样
│   └── repositories/  ←   读写数据的地方
│
├── domain/            ← 🟡 业务层：最核心
│   └── services/      ←   验证、计算、业务流程
│
└── presentation/      ← 🔵 UI层：只管界面
    ├── pages/         ←   页面
    └── widgets/       ←   可复用组件

三层架构的核心规则：只准单向依赖

UI层 → 调 → 业务层 → 调 → 数据层
数据层 → 不知道 (不能调) → 业务层 → 不知道 (不能调) → UI层
                    ↑ 内层绝对不能知道外层的存在

这就像餐厅后厨：

  • 前台可以对接后厨（"客人点了一份红烧肉"）
  • 后厨可以去仓库拿食材（"猪肉不够了，去冷库拿"）
  • 但后厨不能直接跑出去跟客人聊天（业务层不知道 UI 的存在）

怎么判断代码写得好不好？（不用看懂代码）

只需要问三个问题：

① 新功能改了几个文件？
   → 理想情况：加新文件，不动旧文件（说明结构好）
   → 坏情况：改 5 个旧文件才能加一个新功能（说明耦合严重）

② "保存"功能出现在几个地方？
   → 理想情况：只在 data/ 层出现
   → 坏情况：每个页面都有自己的"保存"逻辑

③ 想改报销上限（10000 → 5000）——去哪改？
   → 理想情况：只去 domain/ 层的一个文件
   → 坏情况：搜一下发现有 5 个地方都写了"10000"

这三个问题，比看懂代码更重要。

第三章：MVVM——UI 层内部怎么组织

又一个厨房比喻

🍽️ View（界面层）     = 摆盘 → 菜长什么样，顾客直接看到
📋 ViewModel（中间层） = 配菜师 → 把食材加工成适合摆盘的状态
🧊 Model（数据层）     = 食材 → 原始数据，怎么存的不重要

MVVM 和三层的区别

很多初学者搞混这两个概念，一句话说清楚：

三层架构是"大格局"——整个 App 怎么分三个大区
MVVM 是"小模式"——专门管 UI 层内部怎么和业务层交互

它们不冲突，是搭配使用的。

具体长这样：

三层的大框架：
    presentation/  ← 这里用 MVVM：View = Widget, ViewModel = Provider
    domain/        ← 纯业务逻辑，不知道 UI
    data/          ← 只管数据读写

什么时候需要 MVVM？

情况 需要吗
只有 1-2 个简单页面，数据不共享 ❌ 不需要，用 setState 更简单
5+ 个页面，数据需要跨页面共享 ✅ 需要
同一批数据要在不同页面展示不同样子 ✅ 需要
要写测试 ✅ 需要（ViewModel 可以脱离 UI 单独测试）

第四章：DDD（领域驱动设计）——大项目的分而治之

什么是"领域"？

做报销 App → "报销"就是你的领域
做外卖 App → "外卖"就是你的领域
做记账 App → "账单"就是你的领域

DDD 的核心思想只有一句话：

代码的结构，应该和业务的结构保持一致。

用超市类比理解

三层架构 = 按职能分区的超市
  一个仓库区管所有货
  一个收银区管所有收银
  一个货架区摆所有商品

DDD = 按商品类别分区的超市
  生鲜区有：自己的冷库 + 自己的收银 + 自己的货架
  日用品区有：自己的仓库 + 自己的收银 + 自己的货架

每个区都是一个独立的小超市，各管各的，互不干扰。改生鲜区的规则不会影响到日用品区。

那到底该用什么架构？

这个表格直接照着选就行：

项目规模 推荐架构 状态管理 适合谁
🐣 微型（1-3 页面） 不分层，单文件 setState 个人小工具
🐕 小型（3-10 页面） 简单分层：UI / 逻辑 / 数据 Provider 个人 App MVP
🐘 中型（10-50 页面） 三层架构 + MVVM Riverpod 正式产品
🏢 大型（50+ 页，多人团队） 三层 + MVVM + DDD 思想 Riverpod / Bloc 复杂业务系统

三步快速选型法

第1步：数页面数量
   1-3页 → 微型方案，别折腾
   3页以上 → 继续往下看

第2步：要不要多人协作？
   一个人开发 → 小型/中型
   团队开发 → 中型/大型

第3步：业务复杂吗？
   简单增删改查 → 三层架构足够
   多角色、多流程、多规则 → 引入 DDD 思想

给报销 App 做个诊断

维度 你的情况 结论
页面数 大概 10-20 个 🐘 中型
开发人数 1 人 🐕 小型
业务复杂度 多角色多状态 🔶 中等偏复杂

建议：三层架构 + MVVM（Riverpod）

初创期用三层 + MVVM 打好骨架，增长期用 DDD 思想分疆而治。

这篇的核心收获

① 写代码前先三问：价值锚点？第一动作？Not-To-Do？
② 三层架构 = UI / 业务 / 数据，各管各的
③ 核心规则：只准外层调内层，内层不知道外层的存在
④ MVVM = UI 层内部的组织方式，和三层是搭配关系
⑤ DDD = 大项目时按业务领域分模块，各模块独立
⑥ 不同项目大小用不同架构，不要过度设计
⑦ 小白判断代码好坏：看"改一个功能要动几个文件"就够了
