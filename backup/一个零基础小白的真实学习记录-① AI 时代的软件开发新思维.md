## 第一篇：软件开发的底牌变了

在开始学任何具体技术之前，有一件事你必须先想清楚——

**AI 时代，学软件开发和十年前完全不一样了。**

十年前：
```text
你要学编程语言 → 学语法 → 学框架 → 学工具 → 学部署
每个环节都要自己亲手做
学一年才能做出一个"能看"的东西
```

现在：
```text
你只需要学会"怎么跟 AI 描述你要什么"
AI 帮你写 90% 的代码
你的价值在于：知道要做什么、知道什么不该做、知道怎么验收
```

这不是夸张。下面我就用我自己的经历告诉你，一个零基础的人是怎么在 AI 帮助下，理解整个软件开发流程的。

## 第一篇核心：三个必须知道的概念

### 概念一：什么是 Skills（技能）？

如果你用过 ChatGPT，你肯定遇到过这种情况——同一个问题，它有时候回答得很好，有时候胡说八道。

Skills 就是为了解决这个问题而生的。

**Skills = 给 AI 看的"操作手册"**

比如，你让 AI 帮你做一道菜：
- 没有 Skill：AI 凭自己的"常识"乱做，可能做成黑暗料理
- 有 Skill：AI 按食谱做，每一步都有明确指引

在实际开发中，Skills 长这样：

```yaml
name: github-pr-workflow
description: "Use when creating or reviewing a GitHub Pull Request"
steps:
  1. git checkout -b feature/xxx
  2. 写代码
  3. git commit -m "feat: xxx"
  4. gh pr create --fill
```

当你告诉 AI "创建个 PR"，它加载这个 Skill，就知道该按什么步骤做。

**Skills 的核心理念：** 不是让 AI 自由发挥，而是让 AI 按你的成熟流程执行。

### 概念二：什么是 Agent 开发？

你可能听说过"Agent"这个词，感觉很高大上。其实很简单。

**传统程序和 Agent 的区别：**

```text
传统程序：输入 → [固定的 if/else 逻辑] → 输出
  就像一台自动售货机——投币、选商品、出货，过程是固定的

Agent：   输入 → [大模型 + 工具 + 记忆 + 规划] → 决策 + 行动
  像一个有脑子的助手——你说"帮我订个外卖"，它自己查餐厅、比价格、下单
```

一个 Agent 有三个核心零件：

| 零件 | 是什么 | 打个比方 |
|:---|:---|:---|
| 🧠 **大脑（LLM）** | 理解你的话、做推理决策的大模型 | 人的大脑 |
| 🛠️ **工具集（Tools）** | Agent 能用什么工具（读文件、写代码、搜网页） | 人的手和脚 |
| 📋 **行为规则（Prompt + Skills）** | 什么时候用什么工具、按什么步骤做 | 人的行为准则 |

**一个最简 Agent 的核心逻辑，其实就这么几行（不用看懂，感受一下）：**

```python
class SimpleAgent:
    def __init__(self, llm_client, tools):
        self.llm = llm_client
        self.tools = tools
        self.memory = []
    
    def run(self, user_input):
        prompt = self.build_prompt(user_input)
        response = self.llm.chat(prompt)
        if response.has_tool_call():
            result = self.execute_tool(response.tool_call)
            return self.run(result)  # 递归——做完一步接着做下一步
        return response.text
```

关键在最后一行的**递归调用**——Agent 做一步、看结果、再做下一步，而不是一次输出完就没下文了。

这就是为什么 Agent 能"自主完成一个任务"，而普通 AI 只能"回答一个问题"。

### 概念三：Vibecoding 的三大陷阱

Vibecoding（用 AI 哼着歌写代码）听起来很美好——你说"帮我做个 App"，AI 一口气给你全写出来。

但你试过就知道，这样出来的东西，最初看起来很惊艳，用起来全是坑。

#### 陷阱 1：逻辑稀释

```text
你让 AI 做一个"报销 App"：
→ AI 把 50% 的精力花在按钮颜色、圆角大小、页面动画上
→ 剩下 50% 才用在核心功能（提交报销、审批流程）
→ 结果：UI 花里胡哨，核心功能漏洞百出

这就像你让厨师做一桌菜：
→ 厨师花了 2 小时雕萝卜花做摆盘
→ 主菜随便炒了炒
→ 端上来好看，但不好吃
```

**AI 的注意力是有限的。** 你让它一次做太多，它就照顾不过来。

#### 陷阱 2：技术债堆积——弗兰肯斯坦困境

这是 Vibecoding 最大的坑。

```text
第1次：AI 用 TableView 做列表 ✅ 看起来不错
第2次：你说"加个搜索" → AI 改成 SearchBar + ListView
第3次：你说"加筛选" → AI 改成 CustomScrollView
第4次：你说"加个编辑功能" → AI 用 BottomSheet，和之前的风格完全不搭
```

结果就是一个 App 里，每个控件都有自己的"脾气"——这个页面圆角 8px，那个页面圆角 16px；这个页面用蓝色按钮，那个页面用灰色按钮。看起来像**弗兰肯斯坦**——用不同尸体的零件拼出来的怪物。

**根本原因：AI 没有"全局设计系统"的概念。** 它每次只看你当前的要求，不知道前面做了什么选择。

#### 陷阱 3：反馈断裂

Vibecoding 的精髓是"快速生成 → 即时反馈"——写一段、看效果、再改。

但你让 AI "一次写完所有功能"：
```text
→ AI 埋头写了 2000 行代码
→ 你一看——完全不是你要的样子
→ 想改——不知道从哪改起
→ 重来——又浪费几十分钟
```

**核心原因：AI 的"智力"有上下文边界。** 项目越大，AI 要处理的关系越复杂，一旦超过临界点，AI 就开始"幻觉"——你以为它在写代码，其实它在编造不存在的逻辑。

## 解决思路：三个方法

### 方法一：做减法——什么是 MVP

MVP（Minimum Viable Product，最小可行产品）是解决上面所有问题的钥匙。

```text
不是"这个功能也加上吧"
而是"这个功能能砍掉吗？"

不是"让 AI 一次性做完"
而是"先让 AI 做一个能跑的最小版本"
```

**每加一个功能前先问自己：**
1. 没有这个功能，用户能不能完成核心任务？
2. 这个功能能不能放到 V2？
3. 这个"顺便做一下"会不会增加 3 倍的复杂度？

### 方法二：定规矩——DESIGN_SYSTEM.md

不要让 AI 自由发挥样式。在项目里放一个设计规范文件，每次开发前告诉 AI "先读这个文件"。

```markdown
# DESIGN_SYSTEM.md

本项目 UI 规范：
🎨 颜色：暖棕 #D4A574 / 米白 #F5E6D3 / 暖白底 #FFF8F0
📐 圆角：卡片 20px / 按钮 30px（胶囊形）/ 输入框 16px
🖋️ 字号：标题 18px Bold / 正文 14px / 辅助 12px
📏 间距：卡片内边距 24px / 卡片间距 16px / 页面边距 20px
```

### 方法三：用好 Git 后悔药

每次 AI 改完代码，确认没问题了再 `git commit`。改坏了直接 `git revert` 恢复。

**不需要懂 Git 原理**，只需要记住这个流程：
```bash
AI 写代码 → 你检查 → 没问题 → git commit
                   → 有问题 → git revert → 重来
```

## 这篇的核心收获

```
① Skills = 给 AI 看的操作手册，让 AI 按你的流程走
② Agent = 有大脑+工具+规则的自主执行者，不是简单的问答机器
③ Vibecoding 有三大陷阱（逻辑稀释、技术债、反馈断裂）
④ MVP 思维 = 砍功能比加功能重要
⑤ 定规矩（DESIGN_SYSTEM.md）比 AI 自由发挥靠谱
⑥ Git 是后悔药，AI 时代更不能缺
```
